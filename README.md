# Message Board — Homework 02

A Flutter message board backed by Firebase. Email/password authentication signs people
in, Cloud Firestore stores the messages, and the board updates live from `snapshots()`.

## What's in the app

- `lib/main.dart` — app start, splash screen, and the auth gate.
- `lib/models.dart` — `UserRecord` and `Message`, plus the `Owned` trait both compose.
- `lib/auth_service.dart` — every Firebase Auth call: register, sign in, sign out, auth state.
- `lib/board_service.dart` — every Firestore call for messages: create, stream, update, delete.
- `lib/login_screen.dart` — login and registration form with validation.
- `lib/board_screen.dart` — the live board with edit and delete on your own messages.
- `lib/firebase_options.dart` — generated by `flutterfire configure`, gitignored. The
  committed `lib/firebase_options.example.dart` shows the shape.
- `firestore.rules` — security rules for `users/{uid}` and `messages/{msgId}`.

## Setup

I ran these steps once for the project. Repeat them for your own Firebase project.

1. Create a project in the [Firebase console](https://console.firebase.google.com/).
2. Enable **Email/Password** under Authentication → Sign-in method.
3. Create a **Cloud Firestore** database.
4. Point the app at the project:

```bash
flutter pub get
dart pub global activate flutterfire_cli
flutterfire configure
```

`flutterfire configure` overwrites `lib/firebase_options.dart` with the real values and
writes `android/app/google-services.json`. Both files hold the project's API key, so
both are in `.gitignore` and are not in this repository. A fresh clone has to run this
step before it can build.

5. Deploy the rules:

```bash
firebase login
firebase use YOUR_PROJECT_ID
firebase deploy --only firestore:rules
```

6. Run it:

```bash
flutter devices
flutter run
```

## Run against the emulators

The Emulator Suite needs JDK 21 or newer on `PATH`. The JDK that ships with Android
Studio works:

```bash
export PATH=/path/to/jdk-21/bin:$PATH
firebase emulators:start --only auth,firestore
```

In a second terminal:

```bash
flutter run --dart-define=USE_EMULATOR=true
```

The app points at `10.0.2.2` on ports 9099 (auth) and 8080 (firestore). `10.0.2.2` is
the host machine from inside the Android emulator. The Emulator UI is at
`http://localhost:4000`. Data written there stays in the emulator, so the real project
is untouched.

Seed two test accounts and three messages:

```bash
node tools/seed.js
```

The emulator loads `firestore.rules`, so the denials work there too. Run the denial
checks against the running emulators:

```bash
node tools/rules-check.js
```

It prints one line per attempt with the HTTP code, and exits non-zero if any attempt
does not match what the rules should do.

Two emulator details that cost time:

- The app talks to the `(default)` database. A REST path of `databases/default` is a
  *different* database in the emulator, so the scripts here use `databases/%28default%29`.
- Android blocks plain HTTP by default, so `android:usesCleartextTraffic="true"` is set
  in the manifest. Without it the auth emulator call fails with
  `Cleartext HTTP traffic to 10.0.2.2 not permitted`.

## Auth flow

`main()` calls `WidgetsFlutterBinding.ensureInitialized()` and opens `SplashScreen`.
The splash keeps a `Future<FirebaseApp>` in `initState`. `Firebase.initializeApp` runs
once and a rebuild does not start it again. A failed start puts the error and a Retry
button on screen.

When initialization finishes, `AuthGate` listens to `AuthService.authStateChanges`.
A signed-in user gets `BoardScreen`. A signed-out user gets `LoginScreen`. No other code
picks the route. Killing and relaunching the app lands on the right screen.

Registration calls `createUserWithEmailAndPassword` and writes `users/{uid}` with the
five required fields. The display name is set on the auth user at the same time. The
board reads the author name from there instead of a second document read.

## Data model

| Collection | Fields | Writer |
| --- | --- | --- |
| `users/{uid}` | `uid`, `firstName`, `lastName`, `role`, `registrationDateTime` | The client, once, at registration |
| `messages/{msgId}` | `text`, `authorUid`, `authorName`, `createdAt`, `editedAt`, `schemaVersion` | The signed-in author |
| `users/{uid}/prefs/{docId}` | opt-in fields | The client, for the owner (not used by the UI yet) |

Both documents belong to one uid. That property is the `Owned` mixin in `lib/models.dart`,
and each model supplies its own version of it: `UserRecord.ownerUid` returns `uid`, and
`Message.ownerUid` returns `authorUid`. The rules check the same thing, one path at a
time.

The board collection is public to signed-in users. The user record is private. `role` is
written as `student` and is descriptive only — no rule reads it.

The model classes own the document shape. `toCreateMap` and `toUpdateMap` live on
`Message`, and `toMap` lives on `UserRecord`. The services pass maps around but never
build one.

## CRUD

| Operation | Call |
| --- | --- |
| Create | `BoardService.createMessage(message)` → `messages.add(message.toCreateMap())` |
| Read | `BoardService.getMessages()` → `messages.orderBy('createdAt').snapshots()`, mapped to `List<Message>` |
| Update | `BoardService.updateMessage(message, text)` → `doc(message.id).update(message.toUpdateMap(text))` |
| Delete | `BoardService.deleteMessage(message)` → `doc(message.id).delete()` |

The board reads with `snapshots()`, not `get()`. A message from another device appears
without a refresh. `createdAt` is a server timestamp. The order is the server's order,
not the phone's clock.

## Security rules

- `messages` read: any signed-in user.
- `messages` create: the `authorUid` must equal the caller's uid, the text must be 1–500
  characters, `createdAt` must be `request.time`, and `editedAt` must be null.
- `messages` update: only the author, and `authorUid` and `createdAt` cannot change.
- `messages` delete: only the author.
- `users/{uid}`: read and create only for the matching uid, no update or delete.

The edit and delete buttons are hidden for other people's messages. That is only the UI.
The write is rejected by the rules.

To check a denial, sign in as user B and call `updateMessage` with user A's document id.
The call returns `permission-denied`. A signed-out read of `messages` is denied too.

## Build the release APK

```bash
flutter build apk --release
```

The file lands in `build/app/outputs/flutter-apk/app-release.apk`. The debug manifest's
permission does not carry over to release builds. The release manifest declares
`android.permission.INTERNET` in `android/app/src/main/AndroidManifest.xml`.

The release build signs with the debug key for now. See the
[Android release guide](https://docs.flutter.dev/deployment/android) before publishing
anything.

## Test checklist

The full matrix, with what each run actually showed, is in `EVIDENCE.md`. The short
version:

1. Launch → splash → login screen.
2. Register with a bad email → inline error, no account created.
3. Register properly → board appears, `users/{uid}` has all five fields.
4. Post a message → one document in `messages`, shown on the board.
5. Double-tap Post → still one document (the button is disabled while `_posting`).
6. Edit your message → text changes, `editedAt` is set, "edited" shows.
7. Delete your message → card disappears, other cards stay.
8. Second device posts → first device updates without a refresh.
9. Kill and relaunch → still signed in, board still there.
10. Sign out → login screen; a signed-out read is denied by rules.

## Known limits

- Offline posts sit in the local queue until the connection returns. `createdAt` is null
  until the server stamps it. The card says "sending..." in the meantime.
- No pagination. The board loads the whole collection, which is fine at homework size.
- The rules denials are checked by `tools/rules-check.js` against the emulator, not by
  the Firebase rules unit-testing library.
